# Agent Schema — spec del manifiesto del agente adaptativo

> Estructura de archivos y formato de cada uno. Construye sobre la convención existente de Condor (`trading_agents/<agent>/agent.md`, `config.yml`, `learnings.md`, `sessions/`).
> Última actualización: 2026-05-09

## Estructura de archivos

```
trading_agents/<agent_name>/
├── agent.md              ← prosa de policy + frontmatter mínimo (LLM lo lee)
├── config.yml            ← AgentConfig pydántico extendido con sección `adaptive`
├── invariants.yaml       ← límites duros (NEW)
├── learnings.md          ← memoria pseudo-estructurada (existente)
├── state/                ← memoria persistente (NEW)
│   ├── capital_history/
│   │   └── <bot_name>__<config_name>.jsonl   ← canonical id sanitizado (:: → __)
│   ├── regime_history/
│   │   └── <connector>_<pair>.jsonl
│   ├── controller_performance/
│   │   └── <bot_name>__<config_name>.jsonl
│   ├── audit_log.jsonl       ← cada propuesta + veredicto humano + outcome
│   └── last_changes.json     ← último cambio aplicado por (controller_id, field)
```

**Filosofía**: respeto lo que ya existe (`agent.md`, `config.yml`, `learnings.md`, `sessions/`). Solo agrego `invariants.yaml` y `state/` — son las dos piezas nuevas que hacen falta para el framework adaptativo.

## `agent.md` — policy en prosa

### Frontmatter (YAML)

Solo metadata. Compatible con el formato actual de Condor (`id`, `name`, `description`, `agent_key`, `default_config`).

```yaml
---
id: <auto-generated-hash>
name: Adaptive PMM Supervisor
description: Adapts pmm_mister configs based on market regime and capital state
agent_key: claude-code
adaptive_framework_version: "1.0"     # marcador de framework adaptativo
default_config:
  frequency_sec: 600                  # 10 min (D9)
  execution_mode: loop
created_by: <user_id>
created_at: <iso_timestamp>
---
```

### Body (Markdown, prosa libre)

**Q1=(a)+(c parcial)**: secciones semánticas para que el LLM tenga contexto, **valores numéricos no van acá** (van a `config.yml` y son referenciados sin números).

```markdown
# Adaptive PMM Supervisor

You are a supervisor agent for `pmm_mister` controllers. Your job each tick is
to read three routines, detect controllers in suboptimal regimes, and propose
config changes that move them toward favorable zones. You never modify
controllers directly — your output is a structured proposal that gets:
1. Validated against hard invariants (`invariants.yaml`).
2. Backtested against the suboptimal period (Backtest Evidence Loop).
3. Either applied automatically (`auto` mode), proposed to the human via
   Telegram (`propose` mode), or only logged (`shadow` mode).

## Scope

Controllers under supervision are filtered by `config.yml#adaptive.scope`:
- `bot_names`: which bots to inspect.
- `controller_filter`: which controller types (default: `pmm_mister`).
- `accounts`: which Hummingbot accounts.

## Routines

You read these routines each tick (configured in `config.yml#adaptive.routines`):

1. **`capital_state`** — global wallet state + per-controller capital metrics.
   Critical: check `global.oversub_alerts` first. Any proposal that worsens
   oversub is auto-rejected.

2. **`market_regime`** — multi-timeframe regime classification per
   trading_pair. Read `summary.canonical_regime`, `summary.favorability`,
   and `summary.trigger_candidates` (the framework's a-priori suggestion
   of which dimensions to consider).

3. **`controller_performance`** — performance metrics per controller across
   1h/6h/24h windows. Critical: check `diagnostic.suboptimal_now`. If false
   for all controllers, return `no_action` for the tick.

## Policy

The framework expects you to choose **one dimension** to modify per controller
(not specific values). The Backtest Evidence Loop then expands your dimensional
choice into 3 candidate values and backtests them.

### Default rules

- **Mean-reverting + high vol**: consider raising `take_profit`. The MVP rule
  (D5) — large oscillations mean the current TP captures only part of the
  rebound.
- **Mean-reverting + low vol**: consider tightening `buy_spreads`/`sell_spreads`.
  Few fills, idle capital.
- **Trending up/down (sostenido)**: consider reducing `portfolio_allocation` or
  shifting `target_base_pct` against the trend. The PMM should stay
  inventory-neutral, not accumulate directional exposure.
- **Trending with pullback**: consider biasing `buy_amounts_pct` /
  `sell_amounts_pct` in favor of the macro direction. Operate with bias toward
  where the trend will resume.
- **Random walk + high vol**: consider reducing `max_active_executors_by_level`.
  Don't accumulate executors in uncertain conditions.
- **Optimal regime**: return `no_action`. Don't fix what's working.

### Constraints

- Always read `capital_state.global.oversub_alerts` first. If any asset is
  in `warn` or `crit` severity, prioritize proposals that don't worsen it.
- Never propose forbidden fields (see `invariants.yaml#forbidden_fields`).
- Respect cooldowns implicitly — the framework will reject proposals that
  violate them, but you should reason as if they exist.

### User-defined rules

The user can extend or override the default rules below. Custom rules take
precedence over defaults when there's conflict.

## Mode

The agent runs in one of three modes (configured in `config.yml#adaptive.mode`):

- **`propose`** (default for MVP): every proposal is sent to the user via
  Telegram with [✅ Apply] [❌ Reject] [⏸ Snooze 1h] inline buttons, plus the
  comparative backtest results.
- **`shadow`**: all reasoning happens but nothing is sent or applied. Logged
  to `state/audit_log.jsonl`. Used for validation before going live.
- **`auto`**: proposals are applied directly after passing invariants and
  backtest. Stricter limits apply (see `invariants.yaml#auto_mode`).

## Output format

Per tick, you must return one of:

1. `{"action": "no_action", "reason": "<short string>"}` — when no controller
   needs adjustment.
2. `{"action": "propose", "proposals": [{...}, ...]}` — list of proposals,
   one per controller. Each proposal must include:
   - `controller_id`
   - `dimension` (the field name to modify)
   - `direction` (`"increase"` | `"decrease"`)
   - `magnitude_qualitative` (`"small"` | `"medium"` | `"large"` — the framework
     interprets this into specific values via the deterministic expander)
   - `reasoning` (1-3 sentences explaining the connection between observed
     regime and chosen dimension)
   - `caveats` (optional list — e.g. "take_profit only affects new executors")
```

### Notas del `agent.md`

- **Sin valores numéricos** en el body. Los thresholds, ventanas, cooldowns viven en `config.yml`/`invariants.yaml`.
- **Sección "User-defined rules"** delimitada con HTML comments para que el wizard pueda inyectar/editar sin romper la estructura.
- **Output format** es contractual — el LLM debe respetarlo. La capa de orquestación parsea el JSON.
- **No hay valores específicos en proposals** — el LLM elige `dimension + direction + magnitude_qualitative`. El expansor determinístico de D9 los convierte en candidatos numéricos para backtestear.

Implementación: extender `AgentConfig` con un sub-modelo `AdaptiveConfig`:

```python
class AdaptiveConfig(BaseModel):
    mode: Literal["propose", "shadow", "auto"] = "propose"
    scope: ScopeConfig
    routines: RoutinesConfig
    backtest: BacktestConfig
    notifications: NotificationsConfig

class AgentConfig(BaseModel):
    # ... existing fields ...

```

Si `adaptive` está ausente, el agente corre en modo "legacy" (sin framework adaptativo) y no se cargan invariantes ni state.

## `invariants.yaml` — límites duros

Archivo separado de `config.yml` **intencional**:
- `config.yml` = preferencias del usuario.
- `invariants.yaml` = límites del sistema. Editar requiere conciencia explícita.
- Se versiona con el repo; `config.yml` puede ser local-only.

### Validación de un patch contra invariants

Pseudocódigo del validador:

```python
def validate_against_invariants(patch, invariants, current_state, mode):
    """
    patch: {controller_id: {field: new_value}}
    invariants: parsed invariants.yaml
    current_state: snapshot (capital_state output + last_changes.json)
    mode: "propose" | "shadow" | "auto"
    
    Returns (ok: bool, reasons: list[str])
    """
    reasons = []
    
    # 1. Whitelist / blacklist
    for ctrl_id, fields in patch.items():
        for field in fields:
            if field in invariants.forbidden_fields:
                reasons.append(f"{field} is forbidden")
            elif field not in invariants.allowed_fields:
                reasons.append(f"{field} is not in whitelist")
    
    # 2. Max delta por campo (con multiplier de auto mode)
    delta_mul = invariants.auto_mode.delta_multiplier if mode == "auto" else 1.0
    for ctrl_id, fields in patch.items():
        current_config = get_current_config(ctrl_id)
        for field, new_value in fields.items():
            limits = get_field_limits(field, invariants)
            if not within_limits(current_config[field], new_value, limits, delta_mul):
                reasons.append(f"{ctrl_id}.{field} delta exceeds max")
    
    # 3. Cooldowns (con multiplier de auto mode)
    cd_mul = invariants.auto_mode.cooldown_multiplier if mode == "auto" else 1.0
    last_changes = load_last_changes(state_dir)
    for ctrl_id, fields in patch.items():
        if not respects_cooldowns(ctrl_id, fields, last_changes, invariants.cooldowns, cd_mul):
            reasons.append(f"{ctrl_id} violates cooldown")
    
    # 4. Capital invariants (validate_no_oversub)
    ok, oversub_reason = validate_no_oversub(
        patch, current_state.capital_state,
        safety_margin=invariants.capital.safety_margin
    )
    if not ok:
        reasons.append(f"oversub: {oversub_reason}")
    
    # 5. Backtest requirement (auto mode)
    if mode == "auto" and invariants.auto_mode.require_backtest_evidence:
        if not has_backtest_evidence(patch):
            reasons.append("auto mode requires backtest evidence")
    
    # 6. Circuit breaker
    if invariants.circuit_breaker.enabled:
        reasons.append("circuit breaker is engaged")
    
    return len(reasons) == 0, reasons
```

## Migración de agentes legacy a adaptativos

Pasos para promover un agente existente:

1. Agregar `adaptive_framework_version: "1.0"` al frontmatter de `agent.md`.
2. Agregar sección `adaptive` a `config.yml`.
3. Crear `invariants.yaml` (puede empezar con valores default).
4. Crear directorio `state/` vacío (se va llenando solo).
5. Reescribir el body de `agent.md` con las secciones del schema.
6. Probar en modo `shadow` antes de pasar a `propose`.

Esto **no es prioridad MVP** — el primer agente adaptativo se crea desde cero con esta estructura.
